**HARD RULE (2026-08-20, user-escalated): NEVER wait idle. No exceptions. Full stop.** If nothing is verifiably in flight, you are not "waiting" — you are stalled, and stalled means ACT: ping the agent, verify process state yourself, or do other genuinely useful work. Never write "waiting on the agent" or "holding for X" as a status update unless you have JUST verified, in that same turn, that X is actually alive and doing something. A prior turn's claim that an agent is "running" is not evidence — it decays the instant that turn ends.

**Confirmed failure (2026-08-20, this session):** across several consecutive turns, this session reported "waiting on #1600's remediation agent" / "holding for it to report back" — while the agent had, in fact, already ended its turn with no active task and was doing nothing. The tell was sitting in plain sight: a `SendMessage` call to it returned `"had no active task; resumed from transcript in the background"` — meaning the message just WOKE UP a stopped agent, it did not reach a live one. This was reported as normal progress instead of being caught as "this agent was never running to begin with." The user had to point out `ps aux` showed nothing and call it out directly ("you are bullshitting") before the gap was acknowledged. Separately: Task-tool subagents are NOT separate OS processes — `ps aux` will never show a second `claude` process for a dispatched subagent; only genuine backgrounded shell commands (fast-automation.sh, server-fast-automation.sh, etc.) show up there. Don't conflate "no agent process in ps" with "the agent isn't working" — check the RIGHT signal for the RIGHT kind of background work (see "How to apply" below).

**How to apply — do this EVERY time, not just when a wakeup timer fires:**
1. Before reporting any status that implies ongoing work ("in progress," "waiting on," "still running," "holding for"), verify the actual claim in that same turn — don't recycle a status from an earlier turn.
2. For a **dispatched subagent**: the ONLY reliable signal that it's still doing something is either (a) a harness task-notification that hasn't arrived yet (genuinely means it's still working), or (b) if its last reported message claimed to be waiting/running a background job, verify THAT background job's actual OS-level state (`ps aux`, log file mtime/content) yourself — do not trust the agent's self-report at face value, per [[feedback_subagent_phantom_background_wait]]. If a `SendMessage` reply says "had no active task; resumed from transcript," that is proof the agent was NOT running — say so plainly, don't paper over it as "still working."
3. For a **backgrounded shell command** (fast-automation.sh, server-fast-automation.sh, a reproduction run): `ps aux | grep <command>` is real, cheap, and definitive. Run it before every status update that references that command's state.
4. If verification shows nothing is actually in flight: **do not idle.** Options, in order of preference: (a) ping/resume the stalled agent with a concrete instruction, (b) do independent, non-duplicative useful work (verify a flake yourself, check adjacent state, prep the next step), (c) only as a last resort, tell the user plainly "nothing is currently running, here's the real state" — never dress up genuine idleness as "waiting."
5. When dispatching a background agent or long job, still arm the **10-minute** recurring progress check as before — but the timer is a backstop, not a substitute for verifying state before every status claim.
6. **On EVERY timer/wakeup callback (ScheduleWakeup, Monitor tick, or any periodic check-back) where a dispatched subagent exists: `ListAgents` first, then PING it directly** (`SendMessage`) rather than passively observing its `ps aux`/log state and moving on. User's explicit standing instruction (2026-08-20): "I want you to ping any agents running on all your timer calls." Passive observation alone lets a subagent sit fully stopped (as opposed to a genuine harness task-notification, which fires on its own) between wakeups with nobody nudging it forward — a ping forces it to either report real progress or reveal it had already stopped. Do this even if `ps aux`/logs look like something is progressing; the ping costs nothing and closes the exact gap this whole memory exists to prevent.

**Why this escalation matters:** the softer version of this rule (below) talks about setting timers and detecting stalls "early" — that framing left room for a multi-turn gap between "the agent stopped" and "I noticed and did something about it," which is exactly what happened. The hard rule above closes that gap: verify before you claim, every single time, not just on a periodic check-back.

Do NOT go fully idle and just "stand by" when a background agent, job, or shell is running. Always set a self-wakeup timer (send_later / ScheduleWakeup) and check back frequently to confirm work is actually MOVING — and to detect a stuck/hung job/shell early.

**Why:** A harness completion notification only fires when the agent finishes cleanly. If it hangs, stalls, or the shell wedges, no notification ever comes and hours are lost sitting idle. The user has been explicit: check back often, verify progress, intervene on stalls. This reinforces the global Anti-Passive-Wait rule for THIS session's long agent chains (tdd → review → e2e).

**How to apply:** When dispatching a background agent or long job, immediately arm a **10-minute** recurring progress check — the user's explicit standing instruction: "put a timer to check every 10 minutes on progress when you have agents working". A `Monitor` poll loop that emits one heartbeat line per interval (agent transcript mtime age + size, tree change count) works well and stays silent once no agent is active, so it never spams when idle. On each wake: is the agent still alive? has it produced new output? exceeded expected duration? If moving, re-arm the timer. If stalled past ~2x expected, inspect and intervene (TaskStop the zombie, re-dispatch, or surface to user). Zombie agents that re-notify with "waiting for Monitor" non-answers are done — verify the tree directly and stop them.
